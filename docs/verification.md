# Интерфейс проверяющего ядра 1.0

Контракт: `src/proveryalka/verification/`. Интеграция агента:
`src/proveryalka/agent/verification.py`. Вход — общий BehavioralModel 1.0.
Это интерфейс подключения ядра; компилятор TLA+ и запуск TLC сюда не входят.

## Использование

```python
from proveryalka.agent.verification import verify_dialogue, render_verification

outcome = await verify_dialogue(session)
print(render_verification(outcome))
```

Без адаптера возвращается ENGINE_ERROR, executed=false, engine=null и сообщение
CHECKER_UNAVAILABLE. Проверка и обращения к LLM не выполняются.

Независимый от агента вызов:

```python
from proveryalka.verification import check_behavior, CheckLimits

report = await check_behavior(
    model, checker=adapter, property_ids=[property_id],
    limits=CheckLimits(timeout_seconds=30.0, max_states=100000),
)
```

Адаптер реализует BehaviorChecker: асинхронный метод
`check(request: VerificationRequest) -> VerificationReport`.
Он внедряется явно. Фиктивного движка по умолчанию нет.

## Запрос и лимиты

VerificationRequest содержит schema_version=1.0, model, непустой property_ids,
limits и version_id. Сервер передаёт реальный ID сохранённой версии через
`version_id`; для автономной модели допустим null, она идентифицируется хешем.
Код не выдумывает и не создаёт серверные версии.
None в аргументе property_ids публичной функции означает все свойства.
Пустой список, неизвестные или повторные свойства не запускаются.
Запрос повторно валидируется и копируется. Его изменение адаптером отклоняется.

CheckLimits:

- timeout_seconds: от 0 исключительно до 3600 включительно; по умолчанию 30 секунд
  на весь вызов адаптера;
- max_states: положительное целое, по умолчанию 100000 различных состояний
  на исследование каждого свойства;
- max_depth: необязательный неотрицательный предел глубины исследования свойства.

Предел состояний или глубины означает STATE_LIMIT_REACHED, если вывод не получен.
Доказательный путь не может превышать max_depth. Таймаут оболочки отменяет задачу
адаптера; тот обязан завершить свой subprocess при отмене. Таймаут LLM отдельно
остаётся 300 секунд на запрос. Автоматических повторных проверок нет.

## Результат

VerificationResult относится к одному свойству и самодостаточен, в том числе
при передаче через HTTP:

| Поле | Значение |
|---|---|
| schema_version | 1.0 |
| spec_hash | SHA-256 канонического JSON полной модели |
| version_id | Переданный сервером ID версии либо null |
| mode | engine либо test |
| executed | Был ли вызван адаптер; это не утверждение о старте TLC |
| engine | Настоящие name и version движка либо null |
| limits | Лимиты запроса |
| property_id | ID выбранного свойства |
| status | Один из шести статусов |
| conclusive | Получен ли окончательный вывод о свойстве |
| message | Сообщение движка или конкретная причина ошибки |
| trace | Доказательная трасса или пустой список |
| statistics | Известные счётчики и время, неизвестное — null |
| related_requirements | ID требований, вычисленные приложением |

VerificationReport объединяет результаты одного запуска: schema_version и results.
Модель, режим, движок и лимиты совпадают у всех результатов; повторные свойства
запрещены. В Python доступны report.spec_hash, mode, executed, engine, limits.
HTTP CheckRun.results использует общий VerificationResult.

spec_hash(model) — SHA-256 UTF-8 JSON с сортировкой ключей, без пробелов-разделителей,
ensure_ascii=false и allow_nan=false. Порядок массивов сохраняется. Хеш включает
тексты и ссылки: это идентичность переданного spec, не логическая эквивалентность.

## Статусы

| status | conclusive | Смысл |
|---|---|---|
| PROPERTY_HOLDS | true | Свойство выполнено в проверенной конечной модели |
| PROPERTY_VIOLATED | true | Свойство нарушено в проверенной конечной модели |
| MODEL_INVALID | false | Ядро отклонило модель |
| TIMEOUT | false | Время истекло, вывод о свойстве не получен |
| STATE_LIMIT_REACHED | false | Поиск ограничен состояниями или глубиной |
| ENGINE_ERROR | false | Проверка не выполнена из-за ошибки инфраструктуры |

Окончательный вывод требует executed=true и известных имени/версии движка.
Для mode=test это только тестовый ответ. Отображение всегда предупреждает о тесте.
Таймаут и предел поиска не позволяют объявить свойство выполненным. Завершение
HTTP Run и conclusive различаются: операция может закончиться без вывода о свойстве.

Statistics: states_generated, distinct_states, depth, elapsed_seconds.
Неизвестное не заменяется нулём. Время относится к проверке, а не LLM.

## Проверка трассы

TraceStep содержит number, transition_id и полное state. Номера идут подряд с нуля.
На шаге 0 transition_id=null, state равно начальному состоянию модели. Следующий
шаг ссылается на доступный переход и точно совпадает с его результатом. Типы
и области значений проверяются.

- Нарушение invariant, forbidden_state и deadlock_free требует контрпримера.
- Успешный reachable требует трассы-свидетеля, а не контрпримера.
- Успех остальных свойств и недостижимость reachable не имеют доказательного пути.
- Незавершённая проверка не содержит доказательной трассы. Отладочные данные
  будущий адаптер может хранить в отдельных артефактах.

Проверяется конечный предикат. Для deadlock_free также проверяются отсутствие
доступных действий и недопустимость терминального состояния. Очевидный вывод,
противоречащий начальному состоянию, отклоняется. Это не перебор всего пространства
состояний и не доказательство отсутствия других нарушений: их выполняет TLC.

Хеш, свойства и лимиты должны совпасть с запросом. related_requirements вычисляется
из свойства и переходов трассы в порядке каталога требований. Ответ адаптера
не может подменить это вычисление. Некорректный результат вызывает ошибку,
без преобразования в успешную проверку или альтернативный ответ.

## Агент и история

verify_and_explain выполняет проверку и объяснение. verify_dialogue загружает
последнюю модель сессии: нужен ready без открытых вопросов. Чужая сессия
не принимается. Модель и исходные требования не изменяются.

SDK function tool check_behavior принимает пустой объект аргументов. Модель,
свойства и лимиты привязаны приложением через локальный контекст. LLM не может
их заменить. Разрешён один вызов инструмента, включая ошибочные параллельные
повторы. Предел Runner — два LLM-хода: вызов инструмента и объяснение.
Используются [локальный контекст SDK](https://developers.openai.com/api/docs/guides/agents/define-agents?lang=python)
и [function tools](https://developers.openai.com/api/docs/guides/tools).

VerificationNarrative содержит summary и пояснения выбранных свойств с номерами
реальных шагов; при нарушении может содержать один уточняющий вопрос. Она не
назначает статусы, состояния и требования. Выдуманные
свойства, лишние и пропущенные шаги отклоняются. Верность свободного текста
оценивается отдельно: проверка структуры не доказывает точность объяснения.

При передаче session сохраняются запрос и analyst_verification. Если объяснение
не получено или отклонено, фактический отчёт всё равно сохраняется, explanation=null;
исходная ошибка передаётся вызывающему коду. load_verification восстанавливает
сохранённый результат. Его хеш нужно сравнивать с актуальной моделью перед показом
как результата новой версии. render_verification отображает фактический статус,
состояния и пояснения с обязательной маркировкой теста или невыполненной проверки.

## Подключение ядра

Адаптер принимает тот же BehavioralModel, запускает реальный инструмент и возвращает
VerificationReport с настоящей версией движка, статистикой и трассой. Он соблюдает
лимиты и отмену. Ожидаемая операционная ошибка может использовать CheckerError;
неожиданная ошибка программы не маскируется.

FixtureChecker из tests/test_verification.py — только данные тестов контракта
и SDK, всегда mode=test. Он не включён по умолчанию и не реализует model checking
на Python. Реальный TLC, HTTP-запуски, хранение версий и SSE подключаются отдельно.

## События и сохранённая версия (#17)

`verify_and_explain` и `verify_dialogue` принимают `version_id` и асинхронный
`on_event(event)`. События `tool_started`, `tool_finished`, `tool_failed` содержат
один check_id, ID версии, хеш и выбранные свойства. `tool_finished` содержит
валидированный отчёт; `tool_failed` — диагностику исключения. Событие завершения
отправляется до получения объяснения, поэтому ошибка LLM не превращает
состоявшийся запуск в несуществующий. Сервер может направить эти события в SSE;
сам HTTP/SSE transport здесь не реализуется.

ID версии есть в каждом VerificationResult, проверяется на совпадение с запросом
и сохраняется в истории. VerificationOutcome содержит полный request, report и
необязательное explanation. Снимок модели позволяет воспроизвести бизнес-названия,
области, исходные требования и изменения значений без доверия к пересказу LLM.

`render_verification` выводит фактические начальное состояние и шаги, изменения
переменных, related_requirements, известную статистику, лимиты и границы вывода.
Гипотезы модели находятся отдельно в `hypotheses` и помечаются как неподтверждённые.
Свободный текст объяснения не становится доказательством дополнительных фактов.

## Внешний процесс проверяющего ядра

`CommandChecker` принимает список аргументов локальной команды, без shell и выбора
команды моделью. В stdin передаётся VerificationRequest в UTF-8, stdout должен
содержать один JSON VerificationReport. Логи идут в stderr. Код завершения должен
быть 0, в том числе для обычного PROPERTY_VIOLATED: это результат, а не падение.
Неверный JSON или недоступная команда дают ENGINE_ERROR. Автоматических повторов
и переключения на другой движок нет. При отмене прямой процесс завершается;
управление его дочерними SANY/TLC остаётся обязанностью самого ядра.

Готовый интеграционный пример: `examples/verify_behavior.py`.

```powershell
python examples/verify_behavior.py docs/examples/order.json --version-id <ID_версии> --checker <команда_ядра> <аргументы>
```

Этот пример следует запускать с настоящим ядром после его появления. Он не
содержит запасного checker и не генерирует результат TLC. На текущем этапе
настоящий TLC отсутствует, поэтому интеграционный пункт #17 остаётся непроверенным.
