# SQLite-хранилище (#21)

Сервер по умолчанию подключает `SQLiteBackend`, выполняя миграцию при старте
ASGI lifespan. Импорт модуля и генерация OpenAPI не создают файлы. Путь задаётся
`PROVERYALKA_DATABASE_PATH`, по умолчанию `data/proveryalka.sqlite3`. Для
сохранения между перезапусками этот каталог должен быть постоянным.

Реализованы создание, список и чтение сессий, сохранение текстовых источников
с требованиями. `POST /api/sessions/{id}/sources` принимает
`{"text":"Исходный текст","requirements":["Первое требование","Второе"]}`.
Массив требований задаёт клиент/будущий агент: хранилище не извлекает их с
помощью LLM и не меняет исходный текст. Коды R1, R2… выделяются внутри сессии,
включая требования из нескольких источников. Требования и источник создаются
атомарно, повтор с тем же Idempotency-Key не создаёт дубликатов.

## История и Agents SDK

История хранится **только** в `agent_messages`. Каждая запись содержит JSON
элемента SDK, постоянный UUID и возрастающий sequence внутри сессии. Сохраняются
не только пользовательские сообщения, но и вызовы/результаты инструментов.
`StoredSession` реализует структурный протокол Session (session_id,
session_settings, get_items/add_items/pop_item/clear_session) поверх этой же
таблицы. Методы работают через `asyncio.to_thread`, не блокируя цикл агента.

Таким образом, встроенный `SQLiteSession` SDK **не создаёт вторую историю**.
Это уточнение первоначального плана в README: используется собственный Session
адаптер, допустимый [официальным протоколом SDK](https://openai.github.io/openai-agents-python/sessions/#custom-session-implementations).
Совместимые зависимости сервера и SDK закреплены в `pyproject.toml`.
`proveryalka.agent.runner.run_message(message, session)` принимает этот Session-адаптер
и возвращает текст ответа. SDK читает историю и сохраняет новые элементы через
адаптер; отдельно добавлять то же сообщение в хранилище не нужно.
Используется Responses API с `store=False`: контекст передаётся из нашей базы,
серверное продолжение по `previous_response_id` не используется.
Проверены два реальных хода с LLM и восстановление истории после повторного
открытия SQLiteStore. HTTP-запуски и SSE остаются задачей #24.

В #24 передавайте `StoredSession(store, session_id)` в Runner и не записывайте
тот же input отдельно второй раз в HTTP-обработчике. Пока агент не подключён,
POST messages возвращает 503 без записи фантомного запуска или сообщения.
Согласование транзакций run/сообщений и повторов агентных запусков — #24/#27.

`get_items(limit)` возвращает последние N элементов в прямом порядке, limit≤0
даёт пустой список. `pop_item` атомарно удаляет последний элемент. `clear_session`
очищает только историю, сохраняя сессию, исходные тексты и требования. Sequence
не переиспользуется после удаления. Это внутренние операции SDK, не публичные
HTTP-маршруты удаления.

## Транзакции и миграции

`001_sessions.sql` — первая миграция, версия хранится в `PRAGMA user_version`.
Миграция выполняется в одной `BEGIN IMMEDIATE` транзакции; повторный старт
безопасен. Более новая версия БД вызывает ошибку запуска вместо порчи данных.
Следующая миграция должна быть добавлена отдельно, а не изменять уже применённую.

Каждая операция открывает своё соединение, включает foreign_keys и закрывает
его после commit/rollback. WAL разрешает параллельных читателей; запись
сериализована через BEGIN IMMEDIATE, ожидание блокировки ограничено 10 секундами.
Ошибка SQLite возвращает 503 STORAGE_UNAVAILABLE без путей и SQL в ответе.
Нет постоянных соединений или фоновых потоков, требующих завершения при shutdown.

Идентификатор и номер требования уникальны; составной внешний ключ запрещает
связать требование с источником другой сессии. Доступ к источнику проверяет оба
ID. Это проверка принадлежности данных, **не пользовательская аутентификация**.
Персональные аккаунты и разграничение доступа пока не реализованы.

## Проверка

```sh
.venv/bin/python -m pytest -q
```

Тесты используют временные реальные базы SQLite и проверяют повторные старты,
одновременные повторы запросов, атомарные пакеты сообщений, независимые сессии,
внешние ключи, rollback, параллельное извлечение последнего сообщения, нумерацию
требований, API и структурный Session-адаптер. Интеграционный запуск с реальными
LLM/TLC заблокирован задачами других компонентов и здесь не заявляется.
