# Агент и извлечение требований

Код находится в `src/proveryalka/agent/`. Используются OpenAI Agents SDK,
Responses API и модель `deepseek-v4.1-flash` сервиса МАИ.
Единственный системный промпт — `ANALYST_INSTRUCTIONS` в `prompts.py`.
`create_agent` задаёт его для всех вызовов; извлечение и диалог меняют только
`output_type`, без склейки дополнительных инструкций. Схемы задают формат ответа.

## Диалог

`run_message(message, session)` принимает текст и адаптер Session.
`StoredSession(store, session_id)` загружает и сохраняет единую историю SQLite.
Повторно сохранять те же сообщения в HTTP-обработчике не нужно.

## Извлечение требований (#13)

`extract_requirements(source)` принимает существующий общий тип `Source` из
`proveryalka.contracts` и возвращает `Analysis`. Он не изменяет базу данных.

Пример вызова из Python после установки проекта и заполнения `.env`:

```python
import asyncio

from proveryalka.agent.extraction import extract_requirements
from proveryalka.contracts import Source

source = Source(
    id="example-source",
    session_id="example-session",
    text="Заявку можно отменить.",
)
result = asyncio.run(extract_requirements(source))
print(result.model_dump_json(indent=2))
```

В приложении следует передавать ID существующего источника и его сессии.

Результат содержит объект анализа, требования, сущности, участников, переменные,
начальное состояние, действия со строгими условиями и присваиваниями, предлагаемые
предположения, вопросы о пропусках и противоречия.

Для извлечения и диалога SDK получает один `output_type=DialogueDraft`; его
`analysis` имеет тип `ExtractionDraft`. После получения ответа
приложение проверяет, что каждая цитата дословно содержится в исходном тексте.
Для требований формируются `source_refs` с идентификатором источника, цитатой
и границами фрагмента. Границы — индексы символов Python; `end` не включается.
При повторении одинаковой цитаты указывается её первое вхождение.

При отдельном извлечении идентификатор требования детерминированно зависит от ID источника
и точной цитаты. Изменение формулировки или порядка при сохранении той же цитаты
не меняет идентификатор. Изменение цитаты создаёт другой идентификатор.
Разные требования должны иметь различимые цитаты. Идентификаторы записей БД
и коды R1, R2 назначает существующее хранилище; эта функция их не записывает
и не объявляет результат сохранённым.

Из того же ответа, без второго вызова LLM, собирается `analysis.behavior` по
контракту [BehavioralModel 1.0](behavioral-model.md). Области конечны, условия и
эффекты представлены AST, ссылки и типы проверяются кодом. Неизвестные значения
остаются null; пути неполных данных перечислены в `analysis.model_issues`.
Сборка выполняется в `agent/formalization.py`. TLC на этом этапе не вызывается.
Противоречие в тексте отличается от доказанного нарушения модели.

Промпт сохраняет область действия ограничения (субъект, объект, отрицание,
исключения) и различает описанный механизм с проверяемым требованием к нему.
Запрет не создаёт разрешённое событие. Отдельное требование безопасности
не дописывается к фактическому guard без указания, что такая проверка реализована.
Это общие правила анализа, без привязки к названиям действий и предметной области.
Неупомянутая проверка считается неизвестной, а не отсутствующей. Технический выбор
представления правила не помещается в бизнес-предположения. `contradictions`
описывает несовместимые правила одного назначения; возможное несоответствие
описанного механизма требуемому свойству сохраняется для отдельной проверки.

В ответе LLM новые вопросы имеют единственное место — `questions`.
`analysis.missing_information` вычисляется приложением из открытых вопросов
для удобства вызывающего кода и отсутствует в схеме ответа LLM. Обычно задаётся
один вопрос, максимум два. Неизвестные детали не превращаются автоматически
ни в бизнес-правила, ни в длинную анкету.
Строгие выражения создаются сразу; необходимые для полноты границы и начальные
значения уточняются после того, как понятны обычные действия пользователя.

Пустой вход отклоняется до запроса. Ошибки провайдера передаются вызывающему
коду без повторов. Неверный структурированный ответ допускает ограниченное
исправление, описанное ниже; смены API и подстановки фиктивного результата нет.

## Уточняющий диалог (#14)

`start_dialogue(source, session)` выполняет разбор и возвращает `DialogueState`.
`reply_dialogue(session, message, question_id=None)` учитывает ответ или явную
корректировку и возвращает полный обновлённый разбор. `load_dialogue(session)`
восстанавливает последнее состояние из истории, в том числе после перезапуска.
Тип session — интерфейс Agents SDK; для SQLite используется существующий
`StoredSession`. Код диалога не зависит от FastAPI и конкретного хранилища.

```python
from proveryalka.agent.dialogue import load_dialogue, reply_dialogue, start_dialogue
from proveryalka.contracts import Source
from proveryalka.storage.session import StoredSession

session = StoredSession(store, session_id)
source = Source(**store.get_source(session_id, source_id))
state = await start_dialogue(source, session)
question = state.pending_questions[0]
state = await reply_dialogue(session, "Да, при отмене время освобождается.", question.id)
state = await load_dialogue(StoredSession(store, session_id))
```

Пример ответа применим только к соответствующему вопросу: приложение показывает
пользователю `question.text` и передаёт ID выбранного вопроса. Свободное сообщение
без ID может содержать несколько ответов или явную корректировку. Одно «да»
без выбранного вопроса при нескольких вопросах не должно закрывать их все.

У вопроса есть ID, текст, причина, вид (`missing`, `conflict`, `assumption`)
и состояние (`open`, `answered`, `confirmed`, `rejected`). Предположение хранится
в вопросе отдельно; подтверждённое переносится в правила, отклонённое не должно
использоваться. Закрытые вопросы остаются в истории с ID источника ответа.

Исходный текст не переписывается. Ответы добавляются как отдельные источники
в `state.sources`; новые требования получают ссылки на них. При замене правила
`state.corrections` хранит прежний ID, причину и цитату ответа. Старый разбор
доступен в предыдущем снимке истории. У неизменённых требований сохраняются
ID и исходные ссылки. Все цитаты проверяются по источникам.

В черновике каждого требования LLM указывает `source_id` источника цитаты
и `previous_id` соответствующего требования из предыдущего разбора (или `null`
для нового). Смысловую связь определяет модель: код не ищет совпадения текста
и не угадывает соответствие по совпадению цитат. Неизменённое требование модель
копирует с точным прежним текстом; его редактирование без `corrections` отклоняется.
ID остаётся прежним при другой подтверждающей цитате. Замена бизнес-правила требует
записи в `corrections` и создаёт новый ID с сохранением прежних ссылок.
Код проверяет существование ID, цитаты, состояния вопросов и лимит раундов.
Если требование использует прежний ID, ссылка `previous_id` обязательна даже
при наличии записи об исправлении. Пропуск ссылки не позволяет перезаписать
требование под старым ID.

В запрос передаются источники, актуальный разбор и вопросы. История ответов
и исправлений хранится локально; повторять её в `corrections` не нужно.
Это поле ответа содержит только исправления текущего хода. Снимок диалога имеет
`schema_version: "2.0"`. Для прежнего текстового формата требуется новая сессия:
старая история не удаляется и не преобразуется автоматически через LLM.
Ссылки элементов на прежние требования переводятся через явный `previous_id`
в актуальные ID, включая согласованные исправления.

Статусы состояния:

- `needs_clarification`: есть открытые вопросы;
- `model_incomplete`: вопросов нет, но строгая модель ещё неполна; есть диагностика;
- `ready`: нет открытых вопросов, `analysis.behavior` собрана и проверена;
- `limit_reached`: вопросы остались, но лимит раундов исчерпан.

Промпт выбирает обычно один открытый вопрос, максимум два независимых блокирующих.
Пока есть существенный открытый вопрос, новый не добавляется. Существующий
защитный предел схемы и кода — три открытых вопроса; он не заменяет приоритизацию
и не гарантирует качество выбора моделью. По умолчанию разрешено пять ответных
раундов; `max_rounds` при старте принимает значения от 1 до 10. После достижения
лимита новый вызов модели не выполняется. Для одного шага выполняется запрос
через Responses API с `output_type=DialogueDraft`. Если SDK или общий валидатор
отклоняет формат, типы, ссылки или AST, агент получает диагностику и отклонённый
draft для одной повторной генерации. Всего по умолчанию две попытки; общий helper
`generate_state` допускает от одной до трёх. Исчерпание возвращает `GenerationError`
с числом попыток и диагностикой. Ошибки API и таймауты не перезапускаются.
Смысл требований при исправлении формата менять запрещено. До успешной валидации
в историю ничего не записывается.

Если остались `contradictions` или `assumptions`, но нет открытого вопроса,
ответ отклоняется. Приложение не подставляет вопрос самостоятельно. Неполная
строгая модель получает `model_incomplete`, а не `ready`, с диагностикой
неизвестных полей. Отдельного второго списка вопросов внутри ответа LLM нет.

После успешного получения и проверки результата в единую историю записываются
два сообщения: исходное сообщение пользователя и JSON-снимок состояния аналитика.
Runner для этого вызова не получает `session`, поэтому сам повторно историю
не записывает. При ошибке провайдера или проверки снимок и вход не сохраняются:
вызов можно явно повторить. Вызывающее приложение последовательно обрабатывает
ходы одного диалога; параллельные изменения одной сессии здесь не координируются.

Формат, ссылки и состояния вопросов проверяет код. Смысл ответа, достаточность
уточнения и эквивалентность перефразированных вопросов определяет LLM; это требует
отдельной оценки на реальных сценариях. `ready` означает готовность структуры
BehavioralModel, но не доказывает верность интерпретации или свойства TLC.
HTTP API принимает модель тем же общим классом. HTTP-запуски агента, SSE,
хранение версий и реальный TLC остаются отдельными задачами.

## Проверяющий инструмент

`verify_dialogue(session, checker=adapter)` передаёт готовую модель привязанному
инструменту `check_behavior` и получает объяснение. Формат результата, проверка
трасс, статусы и подключение описаны в [интерфейсе ядра](verification.md).
Без адаптера возвращается `CHECKER_UNAVAILABLE`, `executed=false`, без вызова LLM.
Если объяснение не получено, фактический отчёт сохраняется в истории;
`load_verification(session)` позволяет его восстановить.

## Предлагаемые свойства (#16)

У свойства есть `explanation` с понятным смыслом предиката и `origin`:
`requirement` для явно заданного правила, `proposal` для предложения агента.
Предложение содержит `assumption`, связанный с обычным вопросом подтверждения.
Приложение не генерирует вопросы и свойства по шаблонам бизнес-кейсов.
Один полезный критерий предлагается после выяснения процесса, если критерий ещё
не задан пользователем. Явные ограничения не требуют повторного подтверждения.

До подтверждения остаётся открытый вопрос и `analysis.behavior=null`.
При подтверждении `DialogueState.property_approvals` сохраняет SourceRef ответа;
готовая модель получает `approved_by`. Происхождение `proposal` сохраняется.
Без этого подтверждения общий валидатор не принимает предложенное свойство.
При отказе свойство исключается, вопрос остаётся в истории как rejected;
существующие transitions не меняются. Повторное изменение согласованного
предложения требует нового согласования с новым ID. Смысловое понимание
подтверждения и отказа остаётся задачей LLM, а не поиском ключевых слов в коде.

Семантическая корректность самого свойства не доказывается валидатором AST:
примеры неверного OR вместо AND и отсутствующей переменной находятся в
`docs/examples/property-review.json`. Первое требует проверки по требованиям,
второе отклоняется детерминированным валидатором.

## Проверки

Локальные проверки запускаются командой `python -m pytest -q`.
Примеры для отдельных прогонов реальной LLM находятся в
`tests/fixtures/requirements_examples.json`. Реальные прогоны требуют ключа
из локального `.env` и расходуют квоту провайдера; обычные тесты сеть не используют.
