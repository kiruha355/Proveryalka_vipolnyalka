# BehavioralModel 1.0

Общий контракт конечной модели для агента, HTTP API и проверяющего ядра.
Реализация: `src/proveryalka/behavior/`. [JSON Schema](schemas/behavioral-model-1.0.json).
Изменение смысла полей требует новой версии контракта.

## Получение модели

Агент сразу возвращает требования и строгие выражения. `agent/formalization.py`
обычным кодом собирает модель из тех же данных; второго вызова LLM нет.
Формат ответа всегда DialogueDraft, как для первого разбора, так и для продолжения.
Новые вопросы находятся только в questions. Поле analysis.missing_information
вычисляется кодом из открытых вопросов и не предлагается LLM для заполнения.
Локальные ссылки R1, R2 обозначают позиции в текущем requirements и заменяются
устойчивыми ID. Допустимы также ID прежних требований, явно связанных через
previous_id: приложение переводит их в актуальную версию. Неизвестные ссылки
отклоняются. Смысловая связь по тексту не угадывается.

## Поля

| Поле | Смысл |
|---|---|
| schema_version | Ровно `1.0` |
| name | Непустое название процесса |
| sources | Исходные тексты и ответы одной сессии с ID |
| requirements | Каталог требований: ID, текст, source_refs |
| variables | Непустой список переменных состояния |
| transitions | Разрешённые действия; пустой список задаёт статическую модель |
| properties | Явно заданные проверяемые свойства; список может быть пустым |

Переменная, переход и свойство имеют id, понятное name и непустой список
requirement_ids. ID уникальны внутри раздела и соответствуют
`[A-Za-z][A-Za-z0-9_]{0,63}`. Неизвестные поля запрещены.
Источники и требования также имеют уникальные непустые ID. Ссылка на цитату:
source_id, quote, start, end. Это индексы символов Python: start включён, end нет.
Проверяются границы и точное совпадение с текстом. Связь переходов и свойств
с цитатой проходит через каталог требований, без дублирования исходных фрагментов.

## Состояние

Переменная имеет domain и initial_value:

| domain.kind | Дополнительные поля | Допустимые значения |
|---|---|---|
| boolean | Нет | JSON true, false |
| integer | Целые minimum и maximum, обе границы включены | Целые из диапазона |
| enum | Непустой список различных непустых строк values | Только эти строки |

Начальное состояние однозначно задаётся начальными значениями всех переменных.
false, 0 и строка "0" различаются. Значение должно входить в область. Бесконечные
области, плавающая точка, массивы и кванторы не входят в версию 1.0. Конечные
наборы участников можно представлять enum и отдельными скалярными переменными.
Границы и новые бизнес-правила нельзя выбирать молча ради конечности модели.

## Выражения

| kind | Поля | Значение |
|---|---|---|
| literal | value | Логическая, целая или строковая константа |
| variable | name | Значение объявленной переменной по id |
| unary | op, operand | not для boolean, neg для integer |
| binary | op, left, right | Операция над двумя выражениями |

Бинарные операции:

- and, or, implies: два boolean, результат boolean;
- eq, ne: значения одного типа, результат boolean;
- lt, le, gt, ge: два integer, результат boolean;
- add, sub, mul: два integer, результат integer.

Порядок задаётся деревом. Максимальная глубина — 32 ребра от корня.
Сравнение enum с литералом вне его области отклоняется. Неизвестные переменные,
неизвестные операции, смешение типов и произвольные строки вместо AST запрещены.
Python, TLA+, импорт, атрибуты и вызовы функций не исполняются.

## Переходы

guard — логическое выражение. Явно безусловное действие имеет literal true.
Действие доступно ровно при истинном guard. Несколько доступных действий задают
недетерминированный выбор, порядок списка не задаёт приоритет.

effects — список присваиваний. Пример синтаксиса уменьшения переменной:

```json
{"variable":"free","value":{"kind":"binary","op":"sub","left":{"kind":"variable","name":"free"},"right":{"kind":"literal","value":1}}}
```

Все правые части вычисляются по состоянию ДО действия, затем применяются
одновременно. Неупомянутые переменные сохраняются. Два присваивания одной
переменной запрещены. Пустой список означает отсутствие изменений состояния.
Динамический выход за область — ошибка модели. Нельзя молча добавлять guard
границ или желаемого свойства, чтобы отключить такое действие.
Неявный переход сохранения состояния не добавляется: отсутствие доступных
действий является тупиком, который оценивает deadlock_free.

## Свойства

Каждое свойство имеет kind и логический predicate:

`explanation` объясняет смысл свойства обычным языком. `origin=requirement`
обозначает явно заданное правило, `origin=proposal` — предложенный агентом критерий.
Для proposal обязателен `approved_by`: точная цитата ответа пользователя с ID
источника и границами. Для requirement поле `approved_by` равно null. Неподтверждённое
предложение остаётся в аналитическом диалоге и не публикуется как BehavioralModel.

| kind | Семантика |
|---|---|
| invariant | Предикат верен во всех достижимых состояниях, включая начальное |
| forbidden_state | Ни одно достижимое состояние не удовлетворяет предикату |
| reachable | Существует конечный допустимый путь к истинному предикату |
| deadlock_free | В каждом достижимом тупике истинен предикат разрешённого завершения |

У deadlock_free predicate описывает допустимые терминальные состояния. Для явно
запрещённых любых тупиков это literal false. Неизвестные условия завершения
требуют уточнения. Достижимость не означает достижение на всех путях. Свойства
не меняют guards и effects.

## Неполные сведения

В ответе агента domain, initial_value, guard, effects и predicate могут быть null:
это неизвестность, которая не заменяется true, нулём или придуманным диапазоном.
Известная часть уже содержит строгий AST. Пути неполных данных перечислены в
analysis.model_issues. Готовая модель находится в analysis.behavior и появляется
только после проверки, без неизвестных значений, конфликтов, неподтверждённых
предположений и открытых вопросов.

BehavioralModel.model_validate проверяет структуру, типы AST, все ID и ссылки,
цитаты, начальные значения, области констант и присваивания. Это проверка
вычислимости; верность интерпретации текста оценивается отдельно.
behavior.runtime задаёт эталонную семантику выражений и одного шага. Он не
перебирает состояния и не выдаёт статусы TLC. Реальному ядру нужны компилятор
TLA+, TLC Runner и разбор результата; они здесь не имитируются.

## Совместимость и интеграция

Примеры: [заявка](examples/order.json), [склад](examples/stock.json).
[Схема ответа агента](schemas/analyst-response-2.0.json).
Снимок диалога имеет schema_version 2.0. Старые текстовые условия не преобразуются
автоматически: для нового формата нужна новая сессия. История не удаляется,
загрузка старого снимка сообщает о несовместимости до вызова LLM.

HTTP spec использует этот же контракт: неверная модель получает 422 до адаптера.
Хранение версий, агентные HTTP-запуски, SSE и TLC подключаются отдельно. Перед
запуском проверяющее ядро повторно валидирует полученный JSON.

Между ходами неизменённые переменные, действия и свойства сохраняют ID и AST.
Удаление элемента или изменение выражения без изменения связанных требований
отклоняется. Перестановка одновременных присваиваний и значений enum не считается
изменением семантики. Явная корректировка либо новое связанное требование разрешает
обновление элемента. Предыдущие снимки в истории остаются неизменными.
