Общая архитектура

HTTP API SOKLY6 связывает клиент Mput13, аналитик kiruha355 и ядро TLC kontar0 через строгие контракты. LLM, Java/TLC и Docker выполняют разные операции и возвращают отдельные результаты.

Описание, модель и проверка

Исходный текст и ответы становятся требованиями и моделью. Человек запускает TLC вручную. Аналитик объясняет сохранённый отчёт той же версии; явная правка создаёт следующую версию, сохраняя прежний результат.

Ядро проверки kontar0

Валидатор проверяет DSL, компилятор выпускает TLA+, SANY проверяет спецификацию, TLC исследует достижимые состояния. Парсер восстанавливает контрпример и сверяет его с исходной моделью; отчёт сохраняет смысл и пределы проверки.

Версии, запуски и файлы

Сессия, версия модели, проверка TLC, генерация и запуск pytest хранятся отдельно. Связь с immutable версией и хэшами не позволяет подменить старый результат новой моделью. Миграции 007/008 добавляют изображения и снимки репозиториев.

Генератор и песочница

CodegenService детерминированно превращает согласованную версию в файлы Python + FastAPI + pytest по шаблонам, без LLM. Скачивание ZIP и запуск тестов — отдельные действия; результат pytest не заменяет результат TLC.

Источники, MCP и подключения

TXT/MD/DOCX входят в основной диалог. Изображения, репозитории и MCP уже подключены к create_app, но новых экранов для них нет. Vision возвращает typed extraction, а не готовую BehavioralModel; MCP compare_with_code ограничен точной сохранённой генерацией.

Запуск приложения и CI

Native launcher запускает общее FastAPI-приложение со статикой Vite. SQLite и материалы проверок живут в постоянных каталогах. На схеме показана конфигурация CI jobs; факт их успешного выполнения на GitHub здесь не заявлен.

Что требует ТЗ

Кейс 2 «Разработка агента-аналитика» (Кейс_2_агент_аналитики.docx). Агент получает текстовое описание поведения модуля, строит формальную модель состояний и переходов, передаёт её детерминированному Model Checker и объясняет результат человеку на языке исходных требований. Критерий качества в ТЗ: система успешна, если из неформального описания получена явная модель и проверяемое свойство, проверка запущена, найдена неочевидная допустимая последовательность событий и возвращена человеку как понятный бизнес-сценарий. Генерация TLA+ — промежуточный шаг.

Граница между LLM и TLC

ТЗ разделяет две роли. LLM работает со смыслом и неопределённостью текста. Model Checker работает только с уже формализованной моделью и не использует LLM. LLM не перебирает состояния сама: «вот модель и свойство» — её ответ; «при этих правилах найден путь, нарушающий свойство» — ответ движка.

Отдельное правило ТЗ: агент не исправляет модель автоматически. Контрпример может означать ошибку в требованиях, неверное понимание агентом или пропущенное правило. Агент формулирует гипотезу и уточняющий вопрос; модель меняется только после ответа человека.

Переменные и начальное состояние

Состояние — набор значений всех переменных. В модели заявки три переменные, поэтому одно состояние записывается как (status = Approved, approved = true, cancelled = false). Область значений каждой переменной конечна, иначе перебор невозможен.

В примере ТЗ есть ещё attempts (целое 0..3). В эталонной модели его нет: ни одно правило заявки его не использует. Целые переменные поддерживаются с границами minimum..maximum.

Переходы: условие и изменения

Переход — одно допустимое действие. guard — условие, при котором действие разрешено. effects — новые значения переменных после действия. Переменная, которой нет в effects, сохраняет прежнее значение.

ПереходguardeffectsR
Approve «Согласовать»status = Createdstatus := Approved, approved := trueR2
Cancel «Отменить»status = Created ∨ status = Approvedstatus := Cancelled, cancelled := trueR3
Execute «Исполнить»approved = truestatus := ExecutedR4

Ошибка заложена в паре Cancel/Execute. Условие Execute проверяет признак approved и не проверяет статус. Cancel переводит заявку в Cancelled, но approved оставляет true. Значит, после отмены согласованной заявки Execute остаётся разрешённым. «Только согласованную» в R4 можно понять двумя способами — по статусу или по признаку; модель выбрала признак, и это решение агент обязан показать пользователю.

Как Execute записан в DSL и как он выглядит в TLA+

В модели условие хранится деревом выражения, а не строкой кода:

{"id": "Execute", "name": "Исполнить", "requirement_ids": ["R4"],
 "guard": {"kind": "binary", "op": "eq",
           "left":  {"kind": "variable", "name": "approved"},
           "right": {"kind": "literal",  "value": true}},
 "effects": [{"variable": "status",
              "value": {"kind": "literal", "value": "Executed"}}]}

Компилятор переводит его в действие TLA+ (из Spec.tla настоящего запуска):

\* Исполнить
t_Execute ==
    /\ (v_approved = TRUE)
    /\ v_status' = "Executed"
    /\ UNCHANGED <<v_approved, v_cancelled>>

Штрих v_status' означает значение в следующем состоянии. UNCHANGED явно сохраняет переменные, которых нет в effects.

Как агент должен пересказать этот путь (по ТЗ)

  1. Заявка создана.
  2. Заявка согласована: статус Approved, признак approved = true.
  3. Пользователь отменяет заявку: статус Cancelled, но признак approved остаётся true.
  4. Исполнение проверяет только признак approved, поэтому система разрешает Execute.
  5. Отменённая заявка исполнена — нарушено требование R5.

Вывод — две гипотезы и вопрос к человеку: «отмена должна снимать согласование (approved = false)» или «исполнение должно требовать статус Approved». Агент не выбирает сам.

Исправление и повторная проверка

Acceptance test №2 ТЗ выбирает первую гипотезу: Cancel сбрасывает approved. В модели добавляется одно изменение перехода Cancel; текст R3 обновляется. Различие order_bug.json и order_fixed.json:

  R3: «…можно отменить: статус Cancelled, cancelled=true, согласование снимается: approved=false.»

  Cancel.effects:
    status    := Cancelled
    cancelled := true
+   approved  := false

  TLA+:
-   /\ UNCHANGED <<v_approved>>
+   /\ v_approved' = FALSE

Теперь отмена из Approved ведёт в то же состояние, что отмена из Created: (Cancelled, false, true). Состояние S3 исчезает, вместе с ним — путь к S5. Как вид свойства превращается в проверку TLC

TLC умеет проверять инварианты: формулу, которая должна быть истинна в каждом достижимом состоянии. Все четыре вида свойств сведены к инварианту. Каждое свойство проверяется отдельным запуском TLC со своим Spec.cfg.

ВидИнвариант для TLCTLC нашёл нарушение инвариантаПеребор закончен без нарушения
invariant PPVIOLATED + путьHOLDS
forbidden_state P~PVIOLATED + путьHOLDS
reachable P~PHOLDS + путь-свидетельVIOLATED: цель недостижима
deadlock_free PP \/ guard₁ \/ guard₂ \/ …VIOLATED: тупик в недопустимом состоянииHOLDS

Для reachable смысл обратный: «нарушение» инварианта ~P означает, что путь к цели существует. Поэтому у CanExecute статус HOLDS сопровождается трассой Approve → Execute. Флаг TLC -deadlock отключает встроенную проверку тупиков: тупики оценивает только свойство deadlock_free, где P — допустимые конечные состояния.

Запуск SANY и TLC, лимиты

SANY — анализатор TLA+, проверяет Spec.tla до перебора. Затем TLC запускается отдельным процессом Java; это позволяет ограничить время и принудительно остановить зависший процесс. Команда из manifest настоящего запуска:

java -Xmx512m -XX:+UseParallelGC -cp tla2tools.jar tlc2.TLC -tool -workers 1 -fp 1 -deadlock \
  -noGenerateSpecTE -metadir properties/NoCancelledExecution/states \
  -dumpTrace json properties/NoCancelledExecution/trace.json \
  -config properties/NoCancelledExecution/Spec.cfg Spec.tla

Лимит состояний — дополнительный «сторожевой» инвариант LimitStates == TLCGet("distinct") <= 100000. Его нарушение означает неполный перебор и даёт STATE_LIMIT_REACHED, а не ошибку модели. Глубина ограничивается так же через TLCGet("level"). Верхней границы значений лимитов нет — см. находку F7.

Разбор результата TLC

В режиме -tool TLC печатает сообщения с числовыми кодами. parser.py определяет по ним статус, читает трассу из trace.json, переводит имена действий (t_Approve → Approve), строит changes.json и берёт статистику только из того, что TLC сообщил; отсутствующее значение остаётся null. Затем validate_report сверяет отчёт с запросом: тот же хэш спецификации, лимиты и свойства, трасса воспроизводится по правилам модели, related_requirements пересчитываются.

Что записывается за один сценарий

  1. POST /sessions → строка sessions.
  2. POST /messages с текстом требований → runs (kind=agent); аналитик сохраняет текст в sources, историю — в agent_messages.
  3. Если есть вопросы — события clarification_requested в run_events; ответ пользователя — новый sources (answer_…) и новый ход.
  4. Когда модель готова — models «Analyst model» (одна на сессию), model_versions v1; событие model_proposed.
  5. Пользователь нажимает «Проверить» → runs (kind=check, version_id=v1) → папка файлов → result_json с VIOLATED и трассой.
  6. Пользователь подтверждает исправление → новый ход → model_versions v2 с parent_id = v1. Строки v1 и её проверки не меняются.
  7. Проверка v2 → новый runs → HOLDS. Обе проверки остаются в базе.

Генерация проекта Python + FastAPI + pytest

  1. Человек описывает поведение и отвечает на уточнения.

    LLM выделяет требования с источниками и формализует BehavioralModel: переменные, переходы, guards/effects и свойства. Неясный смысл остаётся вопросом человеку.

  2. Человек просматривает модель и нажимает «Проверить».

    TLC проверяет конкретную неизменяемую версию. LLM объясняет сохранённый отчёт; HOLDS означает отсутствие нарушения в исследованной конечной модели при её условиях и лимитах.

  3. Явная правка создаёт новую версию.

    В выполненном сценарии после VIOLATED человек добавил в guard исполнения NOT cancelled. V1 сохранилась; для v2 человек отдельно запустил TLC и получил HOLDS.

  4. «Согласовать для кода» фиксирует решение человека.
