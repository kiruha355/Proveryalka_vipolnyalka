# Диаграмма модели и файлы проекта

Клиентская библиотека задач #40 и #49. Владение: только `frontend-extensions/`. Backend и основной `frontend/` не изменяются.

```sh
cd frontend-extensions
npm ci
npm run check
npm run demo:build
```

React / react-dom ≥18.2 — peer dependencies. Runtime dependencies: `@xyflow/react`, `fflate`. Основная точка подключения — `src/index.ts`, сборка — `dist/index.js` и `dist/frontend-extensions.css`. Примеры импортируются отдельно из `src/fixtures/index.ts`: запись не попадает в основной клиент.

## Подключение к основному frontend

`workspaceViews` регистрирует `diagram` и `files`; `inspectorSections` — этапы и ссылки на реализацию. Контекст структурно соответствует `frontend/src/public.ts`; внешние поля ядра не импортируются. Основной клиент должен передать `context.createVersion(modelId, {spec,parent_id}, key)`: выполнить POST, обновить список версий и выбрать созданную. Без этого граф доступен для чтения; изменения недоступны с причиной.

Файлы подключаются до рендера приложения:

```ts
import { configureProjectFiles, createCodegenProvider } from '../frontend-extensions/src';
configureProjectFiles({ provider: createCodegenProvider() });
```

По умолчанию HTTP идёт на тот же origin: proxy `/api` к FastAPI. Можно передать `baseUrl` и совместимый `fetch`; при наличии codegen методов в основном API передать собственный `CodegenProvider`. Нужен настоящий router #64, миграция 006 и готовая Docker-песочница для запуска тестов. Без router отображается конкретная причина недоступности. Создание проекта и запуск тестов — отдельные явные действия.

Независимые компоненты:

- `StateGraphWorkspace`: `versions`, `selectedVersionId`, `onSelectVersion`, `results?`, `versionsPort?`, общий `selection?`/`traceStep?` и callbacks. `inspector="edit-only"` оставляет сведения инспектору ядра.
- `ProjectFilesView`: `provider: CodegenProvider`, `currentVersion: VersionRef|null`, `focus?:{path,lines?}`, `onRuleSelect?`, `onManifestLoaded?`.
- `setProjectFocus({path,lines})` открывает точный диапазон при переходе из инспектора/чата; хост вызывает `context.openView('files')`. Диапазоны берутся только из `Generation.files[].elements`, фиктивных путей/строк нет.

## Семантика графа

Узлы — проекции этапов процесса на выбранные переменные. Остальные переменные не фиксируются; остаточные guards видны на условных рёбрах и в инспекторе. Это не граф достижимых состояний TLC. Вычисляемые/неопределённые эффекты не превращаются в придуманный литерал. Ограничение проекции — 48 узлов по умолчанию; для больших моделей есть таблица переходов. Масштабирование, выбор клавиатурой и перетаскивание узлов поддерживаются.

Трасса привязывается к `version_id` и `spec_hash`, затем каждый шаг перепроверяется по DSL: начальное состояние, guard, одновременные effects, неизменные переменные, типы/области. После расхождения дальнейшие шаги не подсвечиваются как подтверждённые. Полные значения и изменения доступны в инспекторе шага. Исходные цитаты требований сохраняются с source id. Редактирование guards/effects создаёт новую версию через реальный POST с `parent_id`, не изменяет исходную и не сохраняет layout в DSL.

## Генерация, файлы и тесты

DTO и маршруты зеркалируют `codegen-integration-contract.md` (#64). Дерево, просмотр текста с номерами строк, связи элементов с моделью и назначения файлов используют реальные metadata. Описание файла — текст детерминированного генератора; оно не выдаётся за ответ LLM. При смене версии/генерации запросы отменяются и состояние просмотра пересоздаётся, запоздалые ответы игнорируются.

`409 VERIFICATION_REQUIRED` открывает явное действие «Создать с текущими результатами TLC». Оно отправляет `allow_unverified:true`; найденное нарушение сохраняется. Это политика реализации генератора, её wording ещё требует пользовательской приёмки. `pytest passed` означает соответствие кода модели на перечисленных состояниях; оно не превращает `violated/inconclusive/not_checked` в `holds`. Подтверждение версии означает «модель отражает требования», а не результат TLC и не согласование бизнес-заявки.

Тесты запускаются отдельно, queued/running обновляются до терминального результата, доступны отмена, ручное обновление и журнал. `null` counts остаются неизвестными. Provenance проверяет generation/version/spec/code hash. Изменение файлов обесценивает старые результаты. Запись `createRecordedCodegenProvider()` доступна только для чтения и явно подписана: она содержит настоящие ответы/ZIP/файлы/pytest из supplied evidence генератора; её ready status реконструирован из receipt, не является live health.

ZIP загружается с реального `/archive`, перед распаковкой сверяются центральный каталог, состав, пути, дубликаты, размеры и обычный тип файлов; после распаковки — каждый SHA-256. Архив пересобирается с обычными правами 0644 из проверенных байтов. Traversal, absolute/Windows paths, case collisions, symlink-like metadata, небезопасный root и несовпадающий code hash блокируют экспорт. Предел архива — 32 МиБ. Текст никогда не исполняется как HTML. Просмотр ограничен 5000 строками с явным сообщением.

Разделители дерева/кода и кода/тестов перетаскиваются pointer-устройством. Стрелки меняют размер, Shift ускоряет, Home/End задают пределы. Доли сохраняются в localStorage; запрет хранилища не блокирует работу. Панели прокручиваются независимо, фокус видим.

## Проверки и границы доказательств

Актуальные результаты — `reports/validation.md`. Vitest/jsdom доказывает компонентные сценарии; запись Docker доказывает работу с поставленными реальными артефактами. Это не live E2E интегрированного frontend/backend. Окончательная визуальная приёмка пользователем pending. Main frontend отвечает за восстановление исходных реплик чата, highlighting выбранных source_refs, кнопку подтверждения версии и проверку всех правил без property-selector/TLC limits form. Эти области здесь не изменялись.
